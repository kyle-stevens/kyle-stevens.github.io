Building a Personal AI Research & Audio Pipeline with Claude Code

How I built a structured workspace that takes a research topic all the way to a finished audio file — using Claude Code for research and synthesis, and a local neural TTS engine for offline voice generation.

Most AI-assisted workflows collapse at the edges: the model produces text, and then you're on your own to do something useful with it. I wanted a system where a topic goes in one end and a finished, publishable artifact comes out the other — consistently, repeatably, without manual stitching between steps.

The result is a small workspace I call the Claude Code AI Agent. It handles research, report synthesis, script generation, and audio rendering as a single connected pipeline. Here's how it works and why it's built the way it is.

The Core Idea

The workspace has three layers. First, plain-text workflow files that define the process in structured Markdown — essentially prompt engineering baked into repeatable instructions. Second, two lightweight Python scripts that handle the compute-heavy work (TTS rendering and model setup). Third, an output directory where finished reports, scripts, and audio files land with consistent naming.

Claude Code acts as the engine driving the workflow files. It reads the instructions, asks clarifying questions, conducts web research, synthesizes findings, and writes the output — all within a single session.

Workflow Files as Reproducible Processes

The key insight is treating AI workflows like code: version-controlled, parameterized, and repeatable. Instead of typing the same context-setting prompts from scratch each session, two Markdown files define the full process.

research.md defines a phased methodology. When invoked, Claude asks clarifying questions first — scope, audience, depth, intended use case — before touching any sources. This single constraint eliminates the biggest failure mode in AI research: generating confident-sounding output that doesn't match what you actually needed.

After the clarifying phase, Claude conducts web searches across 8–10 sources and synthesizes findings into a structured report with a fixed template: summary, key findings, deep dive, content angles, takeaways, and sources. The template enforces consistency and makes outputs easy to scan or hand off.

script-to-audio.md extends the research workflow by embedding a voice script directly inside the report. Spoken lines are marked with Markdown blockquote syntax (>), while stage directions and on-screen notes use separate formatting. This lets the report and its audio script coexist in a single file without the spoken content polluting the written version — or vice versa.

Offline TTS with Kokoro ONNX

For audio generation, I chose Kokoro ONNX — an open-source neural text-to-speech engine that runs entirely offline. The tts.py script extracts blockquoted lines from a report, renders them through Kokoro, and saves the output as WAV or MP3 via FFmpeg.

python tts.py output/2026-06-01-ai-agents-report.md

Kokoro supports 10+ voices across American and British English, with male and female variants at different energy levels. The script picks the voice and speech rate based on a tone parameter embedded in the report header — so a technical deep-dive gets a different delivery than a conversational explainer.

The speech rate mapping was worth thinking through carefully:

  • Calm / explainer: 145 wpm — deliberate, easy to follow
  • Conversational: 170 wpm — natural spoken pace
  • Assertive / punchy: 195 wpm — energetic, suitable for opinionated content

These aren't arbitrary numbers — they're derived from broadcast journalism research on comprehension vs. engagement tradeoffs. Matching voice delivery to content tone makes a real difference in how the output lands.

The offline-first choice was deliberate. Cloud TTS APIs introduce latency, cost per character, and data residency questions. For content that sometimes covers security topics, keeping synthesis local eliminates an entire category of concern.

Model Setup and Dependencies

Kokoro requires two ONNX model files (~300MB total) that aren't bundled with the package. The download_models.py script handles bootstrapping — pulling the files from GitHub releases and placing them in the expected directory. Running it once is all the setup needed.

python download_models.py
# Downloads kokoro-v1.0.onnx and voices-v1.0.bin to ./models/

Runtime dependencies are minimal: numpy, soundfile, and kokoro-onnx. FFmpeg is optional and only needed for MP3 output.

Output Naming and File Structure

Every output file follows a YYYY-MM-DD-topic-slug naming convention. This means the output directory stays sortable, batch processing scripts can glob predictably, and there's never ambiguity about which version of a report corresponds to which audio file.

A completed research session produces three files:

  • 2026-06-01-ai-agents.md — the full report with embedded script
  • 2026-06-01-ai-agents.wav — lossless audio from Kokoro
  • 2026-06-01-ai-agents.mp3 — compressed version via FFmpeg

What Works Well

The clarifying-questions-first constraint is the single highest-value piece of the design. It forces alignment before any work happens, which means the output almost always matches intent on the first pass. Without it, even well-prompted AI research tends to drift toward generic coverage.

Embedding scripts inside reports — rather than as separate files — keeps related assets together and makes the report the single source of truth. Editing the report automatically updates the script; there's no sync problem.

The local TTS stack is fast enough to be practical. A 1,500-word script renders in under 30 seconds on a mid-range CPU, which is well within the threshold where waiting becomes friction.

What's Next

The obvious extension is a watch mode that auto-renders audio whenever a report file changes — removing the manual invocation step entirely. Beyond that, a simple web UI for browsing the output directory would make the finished artifacts easier to review without touching the terminal.

For now, the pipeline does exactly what it was designed to do: take a topic and produce a publishable artifact without manual stitching. That's the constraint worth preserving as the system grows.
