Building an I2C Protocol for Underwater Robotics

How the ASUR robotics team implemented I2C serial communication for thruster motor control — covering the protocol structure, ROS integration, and edge cases in real-time serial I/O.

During my time as Software Lead for the ASUR Underwater Robotics team at ASU, one of the core challenges was getting reliable, low-latency communication between the ROS control layer and the thruster motor controllers. We ended up implementing a custom I2C serial protocol in C++ — here's how it came together and what we learned.

Why I2C

I2C (Inter-Integrated Circuit) is a two-wire serial protocol that supports multiple devices on the same bus, which made it a natural fit for our architecture. We had several thruster controllers that needed to receive commands from a single master controller, and I2C let us address each one individually without running separate wires to every device.

The tradeoff is that I2C is relatively slow compared to SPI, and bus contention has to be managed carefully. For motor control commands that don't require high-frequency updates, the bandwidth was more than sufficient.

Protocol Structure

Each motor command was encoded as a structured byte sequence: a device address byte, a command byte identifying the operation (set speed, stop, query status), and one or two data bytes carrying the value.

// Command packet structure
struct I2CCommand {
    uint8_t address;   // device address (0x00–0x7F)
    uint8_t command;   // command type
    int16_t value;     // signed 16-bit value (-32768 to 32767)
};

std::string encodeCommand(const I2CCommand& cmd) {
    std::string packet;
    packet += static_cast(cmd.address);
    packet += static_cast(cmd.command);
    packet += static_cast((cmd.value >> 8) & 0xFF);
    packet += static_cast(cmd.value & 0xFF);
    return packet;
}

The motor speed values came in as floating-point ROS messages and needed to be mapped to the signed 16-bit range the controllers expected. We normalized inputs in the [-1.0, 1.0] range to [-32768, 32767] before encoding.

ROS Integration

The I2C node subscribed to a geometry_msgs/Twist topic for velocity commands and translated them into per-thruster values using a thruster allocation matrix. Each translated value was then encoded and written to the appropriate I2C device address.

#include <ros/ros.h>
#include <geometry_msgs/Twist.h>
#include <linux/i2c-dev.h>
#include <fcntl.h>

void twistCallback(const geometry_msgs::Twist::ConstPtr& msg) {
    // Allocate twist to individual thruster forces
    float forces[NUM_THRUSTERS];
    allocateThrusterForces(msg, forces);

    for (int i = 0; i < NUM_THRUSTERS; ++i) {
        I2CCommand cmd;
        cmd.address = THRUSTER_ADDRS[i];
        cmd.command = CMD_SET_SPEED;
        cmd.value   = static_cast(forces[i] * 32767.0f);
        writeI2C(encodeCommand(cmd));
    }
}

Edge Cases and Lessons Learned

A few things bit us during testing that are worth flagging:

  • Bus lockup on NAK: If a device didn't acknowledge a transmission, the bus could hang. We added a watchdog that detected stalled I/O and issued a bus reset.
  • Byte ordering matters: We initially had big-endian/little-endian mismatches between the ROS node and the motor controllers. Always be explicit about byte order and test with known values.
  • Timing constraints: I2C writes are blocking in the Linux kernel driver. On a ROS callback thread, this could cause the node to miss its scheduling deadline. We moved I2C writes to a dedicated thread with a command queue.

Result

The final implementation handled reliable thruster control across all axes with sub-10ms latency from ROS command to motor response. The dedicated I2C thread eliminated the scheduling issues, and the watchdog kept us from getting stuck during hardware faults.

If you're doing serial motor control in ROS, the main takeaways are: don't block on I/O in your callback threads, be explicit about data encoding at every boundary, and build recovery logic for bus errors from day one.
