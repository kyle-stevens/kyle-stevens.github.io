Optimizing PostgreSQL Queries in Python with Psycopg2

A look at connection pooling, batch inserts, and cursor reuse patterns that meaningfully reduce query overhead in Python applications backed by PostgreSQL.

Psycopg2 is the most widely used PostgreSQL adapter for Python, but using it naively can leave significant performance on the table. After working with it extensively on data-heavy Python applications, here are the patterns that consistently make the biggest difference.

Connection Pooling

Opening a new database connection for every query is expensive — each one involves a TCP handshake, authentication, and process startup on the server side. Psycopg2 ships with psycopg2.pool, which provides a simple and a thread-safe pool out of the box.

from psycopg2 import pool

connection_pool = pool.ThreadedConnectionPool(
    minconn=2,
    maxconn=10,
    dsn="postgresql://user:password@localhost/dbname"
)

conn = connection_pool.getconn()
try:
    with conn.cursor() as cur:
        cur.execute("SELECT id, name FROM users WHERE active = %s", (True,))
        rows = cur.fetchall()
finally:
    connection_pool.putconn(conn)

For anything handling concurrent requests, ThreadedConnectionPool is the right choice. It keeps a set of live connections ready and avoids per-request overhead.

Batch Inserts with execute_values

Inserting rows one at a time in a loop is the single most common performance mistake. Psycopg2's execute_values helper batches multiple rows into a single INSERT statement, which is dramatically faster above a few hundred rows.

from psycopg2.extras import execute_values

data = [(1, "Alice"), (2, "Bob"), (3, "Carol")]

with conn.cursor() as cur:
    execute_values(
        cur,
        "INSERT INTO users (id, name) VALUES %s ON CONFLICT DO NOTHING",
        data
    )
conn.commit()

The difference is obvious at scale — a loop of individual inserts that takes seconds becomes milliseconds with a single batched call.

Reusing Cursors and Parameterized Queries

Keeping the query string constant across executions lets PostgreSQL cache the query plan. This matters most in tight loops hitting the same query repeatedly.

with conn.cursor() as cur:
    query = "SELECT value FROM metrics WHERE sensor_id = %s AND ts > %s"
    for sensor_id, cutoff in sensor_list:
        cur.execute(query, (sensor_id, cutoff))
        results = cur.fetchall()
        process(results)

Avoid building query strings with string formatting. It prevents plan caching and introduces SQL injection risk — always use parameterized queries with %s placeholders.

Using COPY for Bulk Loads

For truly large data loads, copy_from bypasses the normal query path entirely and uses PostgreSQL's binary COPY protocol — the fastest way to get large amounts of data into the database from Python.

import io

data = "1\tAlice\n2\tBob\n3\tCarol\n"
buf = io.StringIO(data)

with conn.cursor() as cur:
    cur.copy_from(buf, "users", columns=("id", "name"))
conn.commit()

Worth reaching for whenever you're loading more than a few thousand rows at a time.

Summary

The biggest wins, in rough order of impact:

  • Use connection pooling to eliminate per-request connection overhead
  • Use execute_values for batch inserts instead of looping
  • Use COPY for bulk loads of thousands of rows or more
  • Keep query strings parameterized and constant to enable server-side plan reuse

Most of these are straightforward substitutions. If you're doing any meaningful volume with PostgreSQL in Python, they're worth applying immediately.
